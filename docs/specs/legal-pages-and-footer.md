- **다국어(영문 등) 지원** — 이 서비스는 한국어 단일 언어다.
- **쿠키 동의 배너** — 이 저장소는 분석·광고 쿠키를 쓰지 않는다(세션 쿠키 하나뿐,

## 설계 메모

- **개인정보처리방침에 "IP 해시"가 아니라 "IP 원문 저장"이라고 쓰는 이유**: 원본
  코드(`kakao-geocoder` 아님, 리뷰 rate-limit 로직)를 확인하지 않고 원본 개인정보
  처리방침 문구를 그대로 가져왔다면 사실과 다른 내용을 게시할 뻔했다 — 이 저장소의
  `apps/api/src/lib/clientIp.ts`·`reviews.created_from_ip` 컬럼을 직접 확인한 결과
  해시 없이 원문 IP 문자열을 그대로 저장한다(24시간 중복 작성 방지용,
  `review-write-and-report` 설계 메모). 개인정보처리방침은 계약 문구가 아니라
  "우리가 실제로 뭘 하는가"의 서술이라, 원본을 그대로 베끼면 오히려 거짓 고지가
  된다 — 반드시 이 저장소의 실제 코드를 근거로 새로 쓴다.
- **오픈소스 목록을 원본에서 가져오지 않는 이유**: 통제변인 원칙과 별개로, 두
  저장소의 실제 의존성 조합 자체가 다르다(이 저장소는 `@aws-sdk/client-s3`·`sharp`·
  `postgres`·`@hono/zod-validator`를 쓰고 원본과 버전·구성이 다르다). `package.json`을
  직접 확인해 라이선스 필드까지 실제 설치된 패키지에서 읽어 정확성을 확보했다.
- **FAQ를 "준비 중" placeholder로 두지 않고 실제 문답을 쓰는 이유**: 이용약관·
  위치기반서비스약관과 달리 FAQ는 계약적 구속력이 없는 사용법 안내다. 이미
  구현·테스트를 마친 기능(로그인, 리뷰 작성/수정 위치, 신고, 낮은 신뢰도 배지,
  탈퇴 시 익명화)을 사실대로 설명하는 것뿐이라 "전문가 검토 필요"에 해당하지
  않는다고 판단했다. 문구는 원본을 참고하지 않고 이 저장소 자체 화면 문구·라우트
  기준으로 새로 쓴다.
- **Footer를 지도 화면 아래에 두는 이유(스크롤 필요)**: 홈 화면은 지도가 뷰포트
  전체(100vh)를 차지한다. Footer를 항상 화면에 보이게 하려면 지도 높이를 줄이거나
  Footer를 겹쳐 띄워야 하는데, 둘 다 지도가 주된 화면인 이 서비스의 핵심 UX를
  건드린다. 원본도 같은 문제를 "지도 다음에 이어지는 일반 문서 흐름 요소"로
  풀었다(원본은 헤더 높이만큼 지도를 줄여 그 차이가 작을 뿐 구조는 동일) —
  같은 해법을 따르되, 이 저장소는 지도 자체를 줄이지 않는 기존 설계를 유지한다.

  빠져 있던 것도 이 과정에서 발견해 문구를 보강했다.
- **CSS Modules `composes` 미지원 발견**: 처음에 `.preparingCard { composes: card; }`
  형태로 썼다가, 이 저장소의 stylelint 설정엔 CSS-Modules 인식 파서(`customSyntax`)가
  없어 `composes`가 표준 CSS로 파싱되지 않는다는 것을 확인했다 — 이 저장소에 그
  전례가 전혀 없었다. `composes` 대신 기존에 써온 className 문자열 결합 패턴
  (`` `${styles.card} ${styles.preparingCard}` ``)으로 바꿨다.
- **실 브라우저로 6개 페이지 전부 확인**(공개 정적 페이지라 카카오 로그인 불필요):
  홈 화면 푸터의 6개 링크를 실제로 클릭해 `/legal/terms`로 정상 이동, `/legal/privacy`·
  `/legal/oss`·`/legal/location`·`/legal/faq`·`/contact`를 직접 열어 문구·링크
  (`mailto:`, GitHub Issues, 상호 링크)가 전부 정확함을 확인했다.
- **자동화 도구의 스크린샷 표시와 실제 DOM 상태가 어긋난 사례 하나 발견·해소**:
  홈 화면에서 브라우저 pane의 `scroll`/`key` 액션으로 아래로 스크롤을 시도하면
  카카오 지도가 휠·키보드 이벤트를 확대/축소용으로 먼저 소비해 페이지 자체가
  스크롤되지 않는 것처럼 보였고, 스크린샷도 계속 지도만 보여줬다. 하지만
  `window.scrollTo`로 프로그램적으로 스크롤한 뒤 `getBoundingClientRect()`로 직접
  확인한 결과 Footer는 뷰포트 안(`top: 625, bottom: 720`, 뷰포트 720px)에 정확히
  위치해 있었고, 접근성 트리(`read_page`)의 ref로 footer 링크를 실제로 클릭했더니
  `/legal/terms`로 정상 이동했다 — Footer 자체는 정상 렌더링·정상 동작하며,
  스크린샷이 안 바뀐 것은 도구의 캔버스 재캡처 한계로 보인다. 다만 **일반 사용자의
  마우스 휠/키보드로는 지도 위에서 스크롤이 안 먹히고(임베드 지도의 통상적 특성),
  스크롤바 드래그 등 다른 수단으로만 Footer에 닿을 수 있다**는 점은 사실로
  확인됐다 — 지도가 뷰포트 전체(100vh)를 차지하는 기존 설계의 트레이드오프이지
