# 명세: 비속어 필터

- 작성일: 2026-08-25
- 상태: 구현됨

## 목표

원본과 실제 코드를 대조해 발견한 리뷰 모델 격차(`docs/decisions.md` #9)를 좁히는 세 번째
덩이(G). 원본은 리뷰 본문에 비속어가 섞이면 작성·수정 자체를 막는다(422). 이 저장소는
지금 본문 최소 10자 검증만 있고 내용 자체는 걸러내지 않는다. 이 명세는 **작성·수정
시 본문에 비속어가 검출되면 422로 거부**하는 서버 검증을 추가한다.

## 범위 밖

- **클라이언트 측 사전 필터링(타이핑 중 실시간 경고)** — 서버 검증만. 서버가 422를 주면
  `review-list-and-write-ui`에서 이미 만든 `submitError` 표시 경로(`role="alert"`)가
  메시지를 그대로 보여준다 — 이번 덩이에서 UI 파일은 건드리지 않는다.
- **`content` 외 필드 검사** — 신고 사유는 이 저장소에 컬럼 자체가 없다(`review-write-and-report`
  "범위 밖"에서 이미 결정). `dealType`·`dealResult`·`tags`는 화이트리스트 enum이라 애초에
  비속어가 들어갈 수 없다. 닉네임은 카카오가 주는 외부 데이터라 이 저장소가 통제할 수 없다.
- **고도화된 우회 탐지** (초성만 남기기, 특수문자 치환, 유니코드 유사문자 등) — 원본과 동일한
  수준(공백 제거 + 소문자 정규화 후 부분 문자열 매칭)만 구현한다. 더 정교한 탐지는 별도 명세.
- **금칙어 목록을 설정 가능하게 만들기(관리자 화면·DB 테이블화)** — 코드 상수로 고정.
- **원본의 금칙어 목록·구현 코드를 그대로 가져오기** — 통제변인(소스 미복사) 원칙
  (`docs/decisions.md` #9). 정규화 방식(공백 제거+소문자화)과 판정 방식(부분 문자열 매칭),
  422 상태코드라는 **인터페이스 아이디어**만 참고하고 목록·코드는 이 저장소에서 새로 쓴다.

## 수용 기준

**`containsProfanity` (순수 함수, `apps/api/src/lib/profanity.ts`)**

- [x] AC1: 비속어가 없는 정상적인 문장이면 `false`를 반환한다.
- [x] AC2: 금칙어가 포함된 문장이면 `true`를 반환한다.
- [x] AC3: 금칙어 사이에 공백을 끼워 넣어도(예: "금칙어" → "금 칙 어") 정규화 후 검출된다.
- [x] AC4: 영문 금칙어는 대소문자를 바꿔도 검출된다.

**리뷰 작성** (`POST /api/offices/:id/reviews`)

- [x] AC5: 본문에 비속어가 있으면 422와 함께 명확한 에러 메시지를 반환하고, 리뷰는
      생성되지 않는다(repository.insert가 호출되지 않는다).
- [x] AC6: 본문이 정상이면 기존처럼 201로 작성된다(회귀 확인).

**리뷰 수정** (`PATCH /api/reviews/:id`)

- [x] AC7: 본문에 비속어가 있으면 422를 반환하고 리뷰는 수정되지 않는다
      (repository.update가 호출되지 않는다). PATCH는 이 저장소가 이미 확정한 전체교체
      원칙상 항상 `content`를 함께 받으므로 작성과 동일한 검증이 자연히 적용된다.
- [x] AC8: 본문이 정상이면 기존처럼 200으로 수정된다(회귀 확인).

## 영향 범위

- **만질 파일**
  - `apps/api/src/lib/profanity.ts` (신규) — `containsProfanity(text: string): boolean`.
    정규화(공백 제거·소문자화) 후 자체 작성한 금칙어 목록과 부분 문자열 매칭.
  - `apps/api/src/services/reviewService.ts` — `ProfanityError` 에러 클래스 추가,
    `create`·`update` 시작 부분에서 `containsProfanity(params.content)` 확인 후 위반이면
    던진다(기존 `DuplicateReviewError`·`SelfReportError` 등과 같은 타입화 에러 패턴).
  - `apps/api/src/routes/offices.ts`·`apps/api/src/routes/reviews.ts` — `ProfanityError`를
    422로 매핑하는 catch 분기 추가.
  - `apps/api/src/__tests__/unit/profanity.test.ts` (신규) — AC1~4.
  - `apps/api/src/__tests__/unit/reviewService.test.ts`·`officeReviewWriteRoute.test.ts`·
    `reviewsRoute.test.ts` — AC5~8 케이스 추가.
- **새 의존성**: 없음.
- **기존 기능 영향**: 정상적인 본문을 쓰는 기존 흐름(AC6·AC8)은 무변경 — 검증 통과 후
  그대로 진행된다. `review-write-and-report`·`review-deal-and-visit-fields`·`review-tags`의
  기존 AC는 전부 회귀 확인 대상(정상 본문을 쓰므로 영향 없음).

## 설계 메모

- **검증 위치는 서비스 레이어, `packages/types` 스키마가 아니다**: `rating`·`content` 길이
  같은 **형태(shape) 검증**은 zod 계약에 있지만, 비속어 판정은 **비즈니스 규칙**(금칙어
  목록이라는 도메인 데이터에 의존)이라 라우트의 `zValidator`가 아니라 서비스 레이어에서
  처리한다 — `DuplicateReviewError`(DB 제약)·`ReviewRateLimitedError`(레이트리밋)와 같은
  성격이다. 이 판단 기준은 `review-write-and-report` 명세에서 이미 세운 패턴을 그대로 따른다.
- **정규화는 "공백 제거 + 소문자화"만**: 원본과 같은 수준으로 맞춘다. 초성 축약이나
  특수문자 치환 같은 고도화된 우회는 이번 범위 밖 — 원본도 안 하는 걸 여기서 먼저 할
  이유가 없다(비교 실험의 취지에도 맞지 않는다).
- **에러 메시지는 구체적인 금칙어를 노출하지 않는다**: "부적절한 표현이 포함되어 있습니다"류의
  일반 메시지만 반환한다 — 어떤 단어가 걸렸는지 알려주면 필터를 우회하는 정보가 된다.
- **금칙어 목록은 이 저장소에서 새로 작성**: 흔히 쓰이는 한국어 비속어·욕설 위주로 짧게
  구성한다(수십 단어 수준). 완전한 목록을 목표로 하지 않는다 — "명백한 욕설을 막는다"는
  기능 시연이 목적이지, 실서비스급 콘텐츠 모더레이션 시스템 구축이 아니다.

## 열린 질문

없음 — 원본의 정규화·매칭 방식과 422 상태코드만 인터페이스로 참고하기로 확정했고,
검증 위치(서비스 레이어)는 이 저장소의 기존 에러 처리 패턴을 그대로 따르기로 확정했다.

- **AC1~8 전부 확인.** Red→Green: 새 테스트 8개(`profanity.test.ts` 4개 + `reviewService.test.ts`
  2개 + 라우트 2개) 작성 후 전부 실패 확인(`profanity.ts` 파일이 아예 없어 import 자체가

  `TEST_DATABASE_URL`로 통합 테스트 포함 177개 전부 통과).
- **검증 순서**: `create`·`update` 둘 다 비속어 검사를 다른 검증(rate limit·소유권 확인 등)보다
  **먼저** 수행한다 — 원본과 같은 순서(존재하지 않는 리뷰라도 본문이 부적절하면 먼저 걸러낸다).
- **개발 DB 스모크 테스트**: 기존 실로그인 사용자 세션을 스모크 전용으로 하나 심어
  `bun run dev` 서버에 직접 curl:
  - 비속어 포함 작성 → 422, 리뷰 생성 안 됨.
  - 정상 작성 → 201.
  - 비속어 포함 PATCH → 422, 목록 조회로 원래 내용이 그대로 남아있음을 확인(리셋되지 않음).
  스모크 테스트로 만든 리뷰·세션 행은 종료 후 직접 삭제했다.
- **버그 없음**: 이번 덩이는 새 DB 컬럼이 없는(순수 서비스 레이어 검증) 작은 추가라
  ORM 매핑 같은 위험 지점 자체가 없었다. 실제로 발견된 런타임 버그는 없었다.
